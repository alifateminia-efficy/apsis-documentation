# Outbound Flow — Knowledge Transfer Session

## Session Overview

Erik Andersson walks through the complete outbound data flow in the Apsis One Integrations platform — the path data takes from APSIS out to connected CRM systems. The session covers the two types of outbound data (consent updates and activity events), the message pipeline from the SNS topic through SQS, the Audience Subscription Worker, Kafka, Batch Production Workers, and the Outbound Worker. Erik also explains the Broker Service (credential decryption), the Squid Proxy (domain whitelisting), the Generic Connector contract, and the outbound mappings/mapped fields concept used for potential lead creation. ## What APSIS Sends Outbound and Why

There are exactly **two categories** of data sent from APSIS to CRM systems:

1. **Consent** — must be kept in sync between APSIS and the CRM system at all times.
2. **Activity events** — events generated by APSIS tools (e-mail, SMS, form submissions, event tool, etc.).

[Erik Andersson]: > "Everything in the outbound is asynchronous. We have told customers: you can easily expect it to take up to 5 minutes before it appears in the CRM."

---

## Listener Registration — How the Flow Is Triggered (Outbound Manager)

The **Outbound Manager** is the entry point. It is the service that receives sync requests from APSIS tools (e-mail, SMS, form tool, event tool). When a customer activates syncing for an activity or consent subscription, the Outbound Manager registers **event listeners in Audience** for that specific activity or subscription.

Key design principle:
- Listeners are **always scoped to the specific activity or subscription**, never global. APSIS does not say "send us every e-mail event on this account." It says "send us events for *this specific activity ID*."
- For consent, listeners are registered on the specific subscription the mapping covers.

If a customer later **unchecks the sync**, the Outbound Manager:
- Deletes all event listeners in Audience for that activity
- Marks the activity as inactive in the APSIS database (does **not** delete the record — it can be reactivated)

## Message Pipeline: SNS → SQS → Audience Subscription Worker

### SNS Topic and SQS

Audience sends **all events** to a single **SNS topic** inside the integrations platform. The topic dumps everything directly into an **SQS queue** called the **`aud-sub` queue** (Audience Subscription queue).

### Audience Subscription Worker

The `aud-sub` worker (also called the Audience Subscription Worker) consumes from this queue. It:

1. **Reads the message** and determines its type: e-mail, SMS, form, event tool, consent, etc.
2. **Validates preconditions** before processing. The message is **discarded** if:
   - The profile has no CRM ID — profiles without a CRM ID did not originate from the CRM, so sending consent updates for them is meaningless.
   - There is no active installation for this account/section (e.g., the integration was removed but listeners weren't cleaned up during an outage).
   - The feature for this activity type has not been officially released to production (a safeguard against accidentally releasing the listener side of an unreleased feature).
3. **Routes** consent messages differently from event messages (see below).

#### ⚠️ Warning: File Import Can Cause Heavy Load

[Erik Andersson]: > "I had a customer that imported 400,000 profiles with an incorrect CRM ID. The worker was put under heavy load."

Why file import is problematic:
- It can inject a massive volume of events simultaneously (e.g., 60,000 profiles with consent on a mapped subscription).
- It is essentially impossible to validate CRM IDs in advance. A known real-world failure mode: customers export CRM IDs to Excel, Excel auto-formats large integers as floats (adds commas/decimal points), and the import then contains string-formatted IDs that fail CRM lookups with 404 errors.
- Using profile keys as identifiers instead of CRM IDs is "equally bad."

Mitigation: All processing is grouped by `account_section + integration_id + event_type`, so load spikes from one customer primarily affect that customer. Auto-scaling on ECS (CPU-based) will eventually increase capacity, and messages that fail are retried with backoff via the common SQS consumer library. Nothing crashes, but processing slows down.

For e-mail sends at scale: a send to 500,000 recipients generates sent events, delivered events, opened events, clicked events — a large multiplier on the recipient count. These create the most common spikes to the `aud-sub` worker.

## Message Structure Produced by the Audience Subscription Worker

After validation, the worker builds a normalized internal message structure:

| Field | Description |
|---|---|
| `profile_key` | APSIS profile key |
| `event_type` | Type of activity: e-mail, SMS, form, event tool, consent |
| `activity_id` | ID of the specific APSIS activity |
| `correlation_id` | Correlation ID from Audience |
| `source` | Event source |
| `event_time` | Timestamp |
| `event_data` | Raw data from the event (e.g., score for event tool, all field data for form submit) |
| `profile_fields` | Identifying fields: CRM ID, e-mail address, phone number — only populated if the profile has these values |
| `mapped_fields` | Fields configured in outbound mappings (covered later) |

**`profile_fields`** uses the **logical field names from the CRM system** as keys — not generic names. Examples:
- FSC Corporate (E-deal): `per_mail` (person mail), `per_phone`
- Dynamics: `contact_id`, `emailaddress1`

These field name mappings are **static and contractual** — not customer-configurable.

## Consent Messages — Fast Path (Bypasses Kafka/Batching)

Consent updates take a **separate, expedited path**:

- They go **directly from the `aud-sub` worker to the Outbound Worker queue**, bypassing Kafka and the Batch Production Workers entirely.
- Rationale: consent must be updated rapidly, so no batching delay is acceptable.

### Consent Payload Example

```
{
  account_id: ...,
  section_id: ...,
  integration_id: ...,
  subscription_id: ...,        // APSIS subscription (topic)
  consent_type: email|sms,
  consent_status: opt_in|opt_out,
  source: file_import|...,    // recently added metadata field
  ...
}
```

The `source` field is valuable for debugging. If the Outbound Worker logs many 404 errors (CRM ID not found), checking `source: file_import` allows you to conclude the failures originated from a bad file import rather than a systemic integration issue.

## Kafka and Batch Production Workers

### Why Kafka Instead of SQS Here

- Kafka removes certain SQS limitations.
- Easier to connect multiple consumers to different topics.
- **Important**: Kafka is **not an AWS-native service** — it is Apache Kafka, and AWS MSK (Amazon Managed Streaming for Kafka) is AWS's adaptation. This means you do **not** get the same visibility UI as SQS (no queue browser in the console — only the cluster is visible).

### Kafka Topics

There is **one Kafka topic per activity type**: e-mail, SMS, form, event tool, MA flow, etc. The `aud-sub` worker publishes events to the appropriate topic.

### Kafka Configuration and Deployment

- Kafka is deployed via CloudFormation **before** any microservices, as a shared infrastructure resource.
- CloudFormation also sets up: Parameter Store values, ECR repos, SQS queues, SNS topics — all shared resources that microservices depend on.
- Security groups and connectivity are configured in the CloudFormation file.

### Maintenance Note

> Kafka on AWS MSK may require periodic version updates — roughly once or twice a year. Process is: go into AWS console, click "apply update." Erik notes: "So far we've never had any real work with it apart from clicking that update button." — but do not neglect patches.

### Batch Production Workers

There are **6 instances** of the Batch Production Worker, one per Kafka topic:

```
batch-production-worker-email
batch-production-worker-event-tool
batch-production-worker-form
batch-production-worker-ma-flow
batch-production-worker-sms
(+ one more)
```

All run the **exact same Dockerfile and codebase** — the only difference is which Kafka topic each instance listens to. This is purely a configuration difference.

#### Batching Logic

Each consumer reads from its Kafka topic and builds **in-memory batches grouped by installation** (i.e., by account + section + integration). A batch is flushed to the Outbound Worker Queue when either:

1. The batch reaches **200 KB** (SQS limit is 256 KB; 200 KB gives a safety margin)
2. **30 seconds** have passed since the last event for that installation was received

Rationale for 30-second flush: avoids indefinitely waiting for a batch to fill up for low-volume installations (e.g., a single form submission might never reach 200 KB).

Each batch is assigned a **generated UUID** as its batch ID.

## Outbound Worker Queue and Outbound Worker

### Outbound Worker Queue

Standard SQS queue. Contains batches of events, each up to 200 KB.

### Outbound Worker

Reads batches from the queue. For each batch:
1. Identifies the target installation (account ID + section ID + integration ID → determines which credentials and which CRM endpoint to call)
2. Determines the batch type (e-mail events, form events, consent, etc.)
3. Calls the appropriate endpoint on the CRM system via the **Broker Service → Squid Proxy → CRM**

### Final Batch Payload Structure (Example: Form Events)

```json
{
  "batch_id": "<uuid>",
  "integration_id": "...",
  "account_id": "...",
  "section_id": "...",
  "type": "form",
  "profile_data": [
    {
      "fields": {
        "per_mail": "user@example.com"
      },
      "mapped_fields": { ... },
      "profile_key": "...",
      "events": [
        { "event_type": "submitted", "event_data": { ... } }
      ]
    }
  ]
}
```

Events for a single profile are **grouped within the profile's entry** in the batch. E.g., for an e-mail campaign, one profile entry might contain: sent event + delivered event + clicked event.

### Logging and Debugging via CloudWatch

All batch sends are logged with the batch ID:
- Success: `"batch with ID <uuid> was successful"`
- Failure: `"batch with ID <uuid> failed"`

To debug whether a specific batch was sent and whether it succeeded: search CloudWatch for the batch UUID. The full batch contents are logged, so you can inspect exactly what was sent.

CloudWatch log group names match service names (e.g., search for `outbound-worker`, `integration-manager`, `mappings-manager`, etc.).

⚠️ **Warning**: There are many **old CloudWatch log groups from decommissioned Lambda functions** still present. Erik intends to clean these up before the handover is complete. Do not be misled by them. The only Lambda still in active use in the integrations platform is the **Operations Bus Lambda** (triggered on account deletion/termination events, makes requests to internal ECS tasks).

## Broker Service — Credential Decryption and Authentication

### Problem It Solves

Legacy connectors (Lime, FSC Enterprise 12.0) stored API credentials in the database in cleartext (database is encrypted at rest, but developers could read the actual credential values). This is a security design flaw — developers should not be able to see customer credentials.

### Current Design (Generic Connector and newer)

Credentials are **hashed/encrypted before storage** using **KMS**. Developers cannot read the raw credential from the database.

The **Broker Service** sits between the Outbound Worker (and any other service that needs to call a CRM) and the Squid Proxy. It:

1. Reads the encrypted credential for the given installation from the database (**read-only** — never writes)
2. Decrypts it using KMS
3. Adds the correct **Authorization header** to the outgoing request
4. Passes the request along

Developers still never see the actual secret — they only observe whether authentication succeeded or failed.

### Scope

The Broker Service is a **global service** — used by all services that communicate with CRM systems, not just the Outbound Worker. The Integration Manager (used in the inbound flow) also routes through the Broker and Squid Proxy.

The Broker Service is a microservice stored in the main Justin repository, in its own folder.

[Erik Andersson]: > "It's a very stupid service — it has one purpose: read the credential, decrypt it, add it to the Authorization header."

## Squid Proxy — Domain Whitelisting and Security

The **Squid Proxy** sits between the Broker Service and the external CRM. Its sole purpose is **security**: verifying that the target domain is on an allow-list before passing the request through.

### How It Works

1. When an installation is created for any integration, the customer's domain is added to a **`whitelisted_domains` table** in the database.
2. The Squid Proxy checks: does this target domain exist in the allowed list?
   - Yes → passes the request through
   - No → rejects the request

### Configuration

```
# Services are started with the HTTPS proxy environment variable:
HTTPS_PROXY=<squid_proxy_endpoint>
```

Once this environment variable is set, HTTP clients route traffic through the proxy automatically — no custom business logic required in each service.

**Static whitelisting** also exists for known third-party endpoints. Example: Microsoft OAuth/authentication servers are statically whitelisted because Dynamics requires them and they don't change per customer.

### Maintenance Reality

[Erik Andersson]: > "I haven't had to touch this for the past five years. It kind of just exists. The only time you'd need to deal with it is if you introduced a new tool that requires calling some new static endpoint."

A detailed wiki page exists for the Squid Proxy — written by Erik when he originally built it and again when his consultancy contract ended. This is confirmed to still be accurate and up to date (unlike some other wiki pages).

Full Squid Proxy deep-dive is planned as a separate session.

## Generic Connector — Contract Between APSIS and CRM Systems

### What It Is

The **Generic Connector** is a standardized REST API interface specification (documented in a Swagger document) that defines:
- Which endpoints CRM systems must implement
- What request formats APSIS will send
- What response formats APSIS expects

It applies to all "modern" integrations: E-deal/FSC Corporate, FSC Enterprise 12.1, Tribe, and any future integrations.

Legacy connectors (Lime, FSC Enterprise 12.0) use older native APIs and are **not** on the generic connector interface.

### Endpoint Pattern

```
<customer_domain>/v1/<entity_name>/<resource>
```

Examples:
```
GET  <domain>/v1/contact/schema         # retrieve mappable fields
POST <domain>/v1/consents/contacts      # update consent
POST <domain>/v1/events/email           # send e-mail events
```

The entity name changes per CRM (e.g., `contact` for FSC Enterprise 12.1). The endpoint structure and version are fixed by the contract.

### Feature-Gated Endpoints

CRM developers do **not** need to implement every endpoint — only those corresponding to features they declare support for. If a CRM declares support for:
- E-mail campaign sync → must implement e-mail event endpoints
- Form campaign sync → must implement form event endpoints
- Outbound mappings → must support the `mapped_fields` property in event payloads

APSIS will only call endpoints for declared features.

### Versioning Policy

> "We have an agreement with all CRM partners that they should use loose schema validation — they should expect us to send additional properties, but only need to use what they support."

- **Adding** new properties to existing requests → **no version bump required** (backward compatible)
- **Changing or removing** existing properties → **requires a new version** (e.g., `v2/...` endpoints)

So far, a v2 has never been needed. The `source` and `last_updated` fields were added to consent payloads without a version bump.

### Communication Protocol

Any change to the Generic Connector contract must be communicated to **all partners** who have implemented it. Internal Slack/Teams channels exist per partner for this purpose. Erik will add the incoming team to these channels at a later stage.

## Outbound Mappings and Mapped Fields

### Problem Being Solved

In early versions of lead gathering, when a form was submitted, the CRM tried to identify useful fields by **guessing based on field names** (e.g., looking for fields named "first name," "email," "mobile"). This was unreliable — customer field names are arbitrary.

### The Two-Stage Mapping Rocket

**Stage 1 — Form tool mapping** (configured in the form tool itself):
Map the form field name → APSIS profile attribute
- Example: "My custom refrigerator field" → APSIS `email_address` attribute

**Stage 2 — Outbound mappings** (configured on the integration page):
Map the APSIS profile attribute → CRM system field (logical name)
- Example: APSIS `email_address` → CRM field `per_mail`

Both stages must be configured for mapped fields to work. If either is missing, the `mapped_fields` property will be empty or incomplete.

### What the CRM Receives

The `mapped_fields` in the outbound payload tells the CRM: "If you decide to create a new record from this submission, here are the explicitly mapped fields and their values. You should populate `per_mail` with this value, `silhouette_mobile` with this phone number," etc.

### Critical Design Principle

[Erik Andersson]: > "APSIS is never making any request to create new resources in the CRM system. We always just let them know: 'here is a form submit event, do what you want with it.' If they don't respond, we don't care — we have delivered the request."

The **decision to create or not create a lead/contact** is entirely owned by the CRM system. Different CRMs have radically different approaches:
- One CRM always creates a new record on every incoming event and has a human manually review/reject
- Another CRM has fully automated validation logic that accepts or rejects based on data completeness

APSIS is agnostic to this logic. What APSIS does handle uniformly is **processing the CRM's response** — which will be covered in the lead creation session. Possible responses from the CRM:
- No response / no action taken
- "I created a new record from this data"
- "I found an existing match — attached to existing record"

## Consent Payload Sent to CRM (Final Format via Generic Connector)

```json
{
  "record_id": "179",           // CRM ID of the contact (confusingly stored internally as person_id)
  "has_consented": false,
  "source": "file_import",      // optional metadata; CRM can display this in UI
  "consent_base_id": "...",     // derived from the subscription mapping; maps APSIS subscription → CRM consent list/base
  "last_updated": "..."
}
```

⚠️ **Naming confusion**: The internal property name `person_id` is used for what is functionally the CRM ID. Erik acknowledged this naming is "very unfortunate" and historical.

### FSC Enterprise 12.0 — Legacy Consent Handling

FSC Enterprise 12.0 (old version) has **no native concept of consent**. An existing entity called **"profile"** was repurposed/abused to represent a consent base. Note: "profile" in FSC Enterprise and "profile" in APSIS are **completely different concepts** — do not conflate them.

## Service Architecture Summary — Global vs. Flow-Specific Services

```
[APSIS Tools] 
    → [SNS Topic]
    → [aud-sub SQS Queue]
    → [Audience Subscription Worker]
        → (consent fast path) → [Outbound Worker Queue]
        → (events) → [Kafka topics, one per event type]
            → [Batch Production Workers x6]
                → [Outbound Worker Queue]
                    → [Outbound Worker]
                        → [Broker Service]  ← reads encrypted credentials from DB (KMS)
                            → [Squid Proxy]  ← domain whitelist check
                                → [CRM System / Generic Connector Endpoints]
```

**"Global services"** (used by multiple flows, not just outbound):
- **Broker Service** — used by Outbound Worker AND Integration Manager (inbound flow) AND any other service communicating with CRM
- **Squid Proxy** — used by all services communicating with CRM

## Key Takeaways

1. **Outbound flow is fully asynchronous** — consent updates are expedited (skip batching) but events can legitimately take up to 5 minutes to reach the CRM under normal conditions.
2. **Listeners are always scoped to specific activities/subscriptions** — never global. Outbound Manager registers and deregisters these listeners.
3. **File imports are the primary operational risk** — they can flood the pipeline with events for profiles with no CRM IDs or malformed IDs (Excel float-formatting of integers is a known real failure mode). Auto-scaling on CPU mitigates but does not eliminate the slowdown.
4. **Consent takes a fast path** — direct from `aud-sub` worker to Outbound Worker, bypassing Kafka and batching entirely.
5. **Batching uses 200 KB size limit OR 30-second idle timeout** — whichever comes first. SQS 256 KB limit is the technical constraint behind the 200 KB choice.
6. **All 6 Batch Production Workers are identical code** — differentiated only by which Kafka topic they consume.
7. **Broker Service handles credential decryption (KMS)** — developers cannot see raw customer credentials. Read-only access to DB.
8. **Squid Proxy enforces domain whitelisting** — every outbound call to a CRM passes through it. Configuration via `HTTPS_PROXY` environment variable; no per-service business logic needed.
9. **Generic Connector is the contractual interface** — loose schema validation is agreed with all partners; adding properties is safe, removing/changing requires versioning and partner communication.
10. **APSIS never creates CRM records directly** — it delivers event data and the CRM decides what to do. Lead creation response handling is a separate flow covered in the next session.
11. **Two-stage outbound mapping** is required for form-to-CRM field mapping to work: form tool field → APSIS attribute (configured in form tool) + APSIS attribute → CRM field (configured in outbound mappings on the integration page).
12. **Old Lambda log groups in CloudWatch are noise** — ignore them; the only active Lambda is the Operations Bus Lambda.
