## Session Overview

This knowledge transfer session explored the technical architecture and challenges of implementing pre-filled form functionality with CRM integrations in Apsis One. The discussion centered on how form submissions flow through the system, how profiles are resolved across different key spaces, and critical product decisions needed to prevent data corruption and duplicate profiles. Erik Andersson (integration side) and Lukasz Grabowski (form tooling side) combined their expertise to map out use cases, identify gaps in the current implementation, and define acceptance criteria for the pre-filled form feature.

## Form Syncing Architecture: Current State

### How Form Sync Works Today

When a form is created in a section with CRM support (e.g., Efficy Enterprise 12.0/12.1, E-deal, Dynamics), users can enable a **CRM sync option**. This allows the form submission to be synchronized with the external CRM system.

[Erik Andersson]: The workflow operates as follows:

1. **Initial Request**: The form tool fires a request to the integration service indicating that a user wants to sync a specific form activity (with a given ID) to a particular CRM system.

2. **Event Registration**: The integration registers listeners for the events available from that form tool:
   - For standard forms: `open`, `submitted`, `started`, `viewed` events
   - For event tools: all events like `attended`, `cancelled`, etc.

### Form Submission Event Flow

When a customer submits a form, the event travels through this pipeline:

```
Form Submission
    ↓
Audience sends event to Apsis
    ↓
Audience Subscription Worker Queue
    ↓
Event extraction and profile field identification
    ↓
Kafka message (no logs stored here)
    ↓
Form Events Batching Worker
    ↓
Outbound Worker (sends to CRM)
```

### Audience Subscription Worker: Event Transformation

[Erik Andersson]: The audience subscription worker performs critical validation and enrichment:

1. **Event Reception**: Receives the submit event from audience
2. **Profile Field Extraction**: Attempts to extract profile identifiers:
   - CRM ID (rarely present in form submissions)
   - Email address
   - Phone number (SMS)
3. **Validation Logic**: Requires at least one secondary identifier if CRM ID is missing:
   > "If there is no CRM ID then we require there to be like either an SMS or an e-mail. Because that's the secondary like type of identification. If there is no CRM ID, if there's no e-mail address and no SMS, then like this, this submission is like useless. We we can't do anything with it because we can't attach it to any existing resource like the first name and or last name like that's that's not enough."

4. **Additional Fields Added**: The worker adds ritual fields needed downstream:
   - Activity ID
   - Event timestamp
   - Event type
   - Profile key (generated by audience for public forms)

### Profile Key Spaces for Public Forms

[Lukasz Grabowski]: For public forms, the profile key space depends on the primary identifier provided:
- If email is entered → profile created in **email key space**
- If phone number is entered → profile created in **SMS key space**

[Erik Andersson]: This is significant because the profile doesn't initially exist in the CRM's custom key space (e.g., `FSC_Enterprise_12.1` key space for Efficy Enterprise).

### Batching and Outbound Worker

[Erik Andersson]: After the audience subscription worker validates the event:

1. **Batching**: The form events batching worker collects submit events and groups them into batches with generated batch IDs
2. **Sending**: The outbound worker attempts to send the batch to the CRM system
3. **Retry Logic**: If the CRM system is unavailable (e.g., 504 response), retries are performed up to a certain level

## CRM Response Handling and Profile Merging

### Three Possible CRM Responses

[Erik Andersson]: When Apsis sends a form submission event to the CRM system, three outcomes are possible:

#### 1. No Action / Empty Response
The CRM responds with an empty or minimal response, effectively saying "I received this but I'm not doing anything with it." In this case:
- Nothing happens in Apsis
- No profile update occurs
- No CRM ID is returned

#### 2. Matched Record Response
The CRM finds an existing contact matching the email or phone number:
```
{
  "matched_records": [
    {
      "profile_key": "<apsis_profile_key>",
      "crm_id": "<external_crm_id>"
    }
  ]
}
```

**Flow**:
- CRM identifies an existing contact with matching email/phone
- CRM responds with the CRM ID for that contact
- Apsis adds the CRM ID as an attribute to the form-created profile
- **Merge worker** is triggered to merge the form profile with the existing CRM-keyed profile

#### 3. New Record Response
The CRM creates a new contact:
```
{
  "new_records": [
    {
      "profile_key": "<apsis_profile_key>",
      "crm_id": "<new_external_crm_id>"
    }
  ]
}
```

Same merge flow applies as matched record.

### Why Merging is Critical

[Erik Andersson]: The merge is essential for future delta syncs:

> "In the future, if the CRM system sends us a real-time update in the Delta Sync worker flow, we don't create a duplicate in Apsis because if you have [only] the profile submitted from the form with the e-mail and we had added the CRM ID, that profile would not have been found when we do the profile updates in the real time sync because we only look in our custom custom key space."

The **Apsis custom key space** (e.g., `FSC_Enterprise_12.1`) uses the CRM ID as the key. When the CRM sends updates via delta sync, Apsis searches in this key space. If the form-created profile exists only in the email key space and was never merged into the custom CRM key space, updates would not reach it.

### Key Principle: No Attribute Updates from Apsis

[Erik Andersson]: This is a critical architectural rule:

> "We are just letting them know like yo someone submitted this uh form like do what you want with it. ... We are not updating any profile like if they entered like a first name or last name. Apsis is never making any like actual attribute updates in the CRM system like we are not updating first names or last name or adding emails."

The integration only notifies the CRM of the event. The CRM decides whether to:
- Create a new contact
- Link the event to an existing contact
- Create an internal event entry

But Apsis never modifies contact attributes in the CRM. This is because **the CRM is the master data source**.

## Pre-Filled Form Functionality

### What Pre-Filled Forms Enable

[Lukasz Grabowski]: Pre-filled forms are currently behind a feature flag and allow sending form links to specific profiles rather than public forms. When a user opens the form via a personalized link:

- The system recognizes the specific profile
- Form fields are pre-populated with data from that profile
- The user can view and optionally update their information

### Demo Scenario: Sending Pre-Filled Form to CRM-Synced Profile

The team demonstrated a realistic use case:

3. **Form Send**: Sent the form via email to this CRM-sourced profile

## The Duplicate Profile Problem: Root Cause Analysis

### The Risk Scenario

[Erik Andersson]: When a profile exists only in the CRM key space (synced from the CRM, not yet merged with email key space):

> "So yeah, we will need to verify this. ... If we sync it from the CRM to Apsis, but that is the only thing that has happened, then there is no link to the e-mail key space. So we we will need to. We will need to verify this."

**Problematic Flow**:
1. Profile is synced from CRM → exists in `FSC_Enterprise_12.1` key space with CRM ID
2. Pre-filled form is sent to this profile
3. User opens form via personalized link → system identifies profile
4. User submits form (optionally updates email address)
5. **Unknown behavior**: Form tool creates event on profile using which key space?
   - If email key space only → new profile is created there
   - If not merged with CRM key space → duplicate profiles exist in Apsis
   - When CRM sends delta sync update → update goes to CRM key space, not the email key space profile

### The Proposed Test Case

[Lukasz Grabowski]: To verify the current behavior:

1. Create a contact in the CRM with a specific email
2. Sync that contact to Apsis (exists in CRM key space only)
3. Send a pre-filled form to that profile
4. Submit the form
5. Verify: Search by email and search by CRM ID return the **same profile ID**

## Protecting CRM Master Data: Architecture Decisions

### Principle: Data Flows One Direction

[Erik Andersson]: The foundational rule is:

> "The data on the profile inside of Apsis One should not be overwritten because what you do here is that you introduce discrepancies which like the whole integration platform is about protecting the data from discrepancies."

**Why This Matters**: 
1. CRM is the master data source
2. If a profile is synced from CRM with `first_name = "Eric"` and the user submits a form claiming `first_name = "Henrik"`:
   - Current data in Apsis becomes "Henrik"
   - CRM still has "Eric"
   - When CRM sends delta sync, Apsis overwrites form data with "Eric" (CRM's version)
   - User sees incorrect data until next sync
   - Creates data discrepancy windows

### Approach 1: Block Overwrites for Mapped Fields

Use the **Mappings Manager Service** to detect which fields are CRM-synced:

```
1. Check if integration exists on section
2. Look up integration ID in Mappings Manager
3. Retrieve field mappings (Apsis 1 field → CRM field)
4. In form submission:
   - Allow updates to unmapped custom attributes
   - Block updates to fields in the mapping
   - Prevent updates to CRM ID field entirely
```

[Erik Andersson]: The CRM ID field is the absolute critical one:

> "And there is, there is one absolute big no, no, which I think you might actually be able to do. Let's say now that you add a. You add a field and I don't know if you are able to add the mapping to CRM ID... if you for whatever reason would would be able to actually update your CRM ID. I can tell you that we will be in deep **** because this is one of the things you can under no circumstance do if you have an integration because we will. Lose complete track of that profile. Then you will definitely introduce duplicates."

### Distinguishing CRM Fields from Enrichment Fields

[Erik Andersson]: There are two categories of data:

1. **Mapped CRM Fields** (e.g., First Name, Last Name, Email synced from CRM)
   - These are write-protected from forms
   - Master copy lives in CRM
   - Apsis is read-only for these fields

2. **Enrichment Attributes** (e.g., Customer Satisfaction Rating, Favorite Color)
   - Not present in CRM
   - Specific to Apsis marketing operations
   - Can be freely written from forms

> "Say that you have this like customer satisfaction attributes like this is not something you would typically have inside the CRM system whereas it might be a good. Like marketing data to have inside of Apsis. So if you add a completely new attribute which is not mapped in the CRM system, of course that is completely OK to add from the form..."

### Critical Caveat: No Back-Sync of Enrichment Data

[Erik Andersson]: This is essential for Henrik to understand:

> "But then the important disclaimer, this data will not exist in the CRM system. It will only exist in APSIS because we don't support the sinking of attribute changes in. Apsis to the CRM, just so Henrik is also aware of this and not like, yeah, yeah, we collect all cool data in Apsis and it is automatically added in. In the CRM. Because of the point number one like support enrichment of CRM SMS profiles via form link, we will support it by enriching them in abscess, but we do not support enriching them. In the CRM."

**Summary**: 
- Enrichment attributes can be collected in forms → stored in Apsis
- These attributes will NOT sync back to the CRM
- CRM remains the master for all its mapped fields
- This is by architectural design, not a limitation

## Form Tool Implementation Requirements

### Requirement 1: Ensure Correct Profile Resolution

**Goal**: When a pre-filled form is submitted, the form submission event must be recorded on the correct profile, with no duplicates created.

**Implementation Approach**:
1. When form is submitted, the form tool receives the profile identifier (email, CRM ID, etc.)
2. Must query Apsis to determine which profile(s) match this identifier
3. Check if a CRM integration exists on the section
4. If integration exists and profile has CRM ID:
   - Verify profile also exists in CRM key space
   - If not merged, trigger merge before recording event
   - Record event on merged profile (single ID)

[Erik Andersson]: The test for correctness:
> "If you search for the e-mail and go to the profile, it should have the same ID as if you search for the CRM ID and go to the profile. If that is the case, everything is good. But if you search on the e-mail, you get one's profile ID and then you search for the CRM ID and you get another ID... then we need to go back to the drawing board with that flow..."

### Requirement 2: Protect CRM Master Data from Being Overwritten

**Implementation Options**:

**Option A**: Block all updates to fields that exist in CRM mappings
```
if (profile.has_crm_id && field_in_crm_mappings(field_name)) {
  reject_form_update()
}
```

**Option B**: Allow updates but with warnings shown to user
- Display in form: "This field syncs from CRM and will be overwritten on next sync"

**Option C (Recommended)**: Hide CRM ID field entirely from form editor

[Michal Rosikiewicz]: Proposed: Hide CRM ID field from the form field editor when an integration is present on the section.

> "If you have integration on a section, hide CRM ID if you don't have it."

[Erik Andersson]: This should be done only once during form creation:
> "I would assume that you keep that data between the steps here. So if you've made the request once, you will know if you should show this sync to CRM and you will know if you should. The integration or not, if you do the request to integration like in the last step or in the first step, I don't think that should really matter. You should do it like in the first time you need it and then preserve that data until the flow is done."

### Requirement 3: Allow Enrichment of New Attributes

Forms should allow creation and storage of custom attributes that don't exist in CRM mappings. These become enrichment data in Apsis only.

[Erik Andersson]: The distinction is clear:
> "If you introduce. Use a new form field called satisfactory rating which you have mapped to a completely standalone attribute inside of apps is called like satisfactory rating. Then of course you can add that new data to the profile in. In absence because we will not touch it when we do the sinks because there is no field mapping like that is completely fine."

### Requirement 4: Provide Smooth End-User Experience

This is not an integration concern but a form UX decision about whether form submissions should allow overwriting mapped fields or not.

[Erik Andersson]: From integration perspective:
> "The only real decision there is to be had is like should you allow the data to be overwritten in Apsis knowing that we will completely override it on the next sync? Or should you prevent the update of the data in Apsis to not allow for discrepancies like this is more a product question because like from the integration side like nothing will break for us."

### Requirement 5: Consent Handling (Bidirectional)

Unlike regular attributes, **consent is bidirectional** and legally required to sync both ways.

[Erik Andersson]: When a user modifies consent in a form:
- If they grant consent to a subscription with CRM mapping → integration sends update to CRM
- If CRM has no consent → form pre-fill should show no checkbox (currently broken)
- This is a form tool fix needed

> "Here there are legal reasons as to why we need to have a bidirectional sync. So like this, this should already work out-of-the-box, but [form tool needs to] fix the pre-fill..."

## Technical Architecture: Key Concepts

### Key Spaces Explained

Apsis One uses isolated key spaces to identify profiles. For each CRM integration, a custom key space is created:

- **Email Key Space**: `profiles/${account}/email/${email}`
- **SMS Key Space**: `profiles/${account}/sms/${phone}`
- **CRM Custom Key Space**: `profiles/${account}/FSC_Enterprise_12.1/${crm_id}` (example for Efficy Enterprise 12.1)

[Erik Andersson]: 
> "So it's because we have a CRM key space which is bootstrapped by. I don't know if it is audience or you, we are not using that. So we have our own custom key space. ... For each integration you have own [key space]. ... In this case it would be a FSC Enterprise 12.1 key space where the CRM ID happens to be the key."

**Why Multiple Key Spaces**:
- Allows profile lookup by any identifier (email, phone, CRM ID)
- Enables merging when new identifiers are discovered
- Prevents duplicates when same person is identified multiple ways

### Profile Merge Mechanism

When a form submission brings new information that links to an existing profile:

1. Audience subscription worker identifies the linking identifier (usually email)
2. CRM system responds with the matching CRM ID
3. Merge worker combines the profiles:
   - Creates link between email key space and CRM key space
   - Single profile ID used going forward
   - CRM updates now apply to merged profile

[Lukasz Grabowski]: Verified the merge:
> "So if we search for the e-mail and go to the profile, it should have the same ID as if you search for the CRM ID and go to the profile."

## Key Takeaways

1. **Pre-filled forms are architecturally feasible** but require careful handling of the CRM key space to avoid duplicate profiles.

2. **CRM is the master data source**: Attributes mapped from the CRM should never be overwritten by form submissions. This prevents discrepancies between Apsis and the CRM system.

3. **Enrichment attributes are Apsis-only**: New custom attributes collected via forms stay in Apsis and do not sync back to the CRM. This is by design.

4. **Merging is critical**: When a form submission links a new profile to an existing CRM contact, a merge worker must create the connection. Without this, delta syncs won't reach the form-created profile.

5. **Three key decisions needed**:
   - How should form tool prevent CRM-mapped field overwrites?
   - Should enrichment data sync back to CRM? (New feature if yes)
   - Should field-level audit logs be implemented?

6. **Form tool must query Mappings Manager** to know which fields are CRM-synced, so it can protect them from being overwritten.

7. **CRM ID field is critical**: It must never be editable in forms, as changing it would cause Apsis to lose track of the profile and create duplicates.

8. **Consent is bidirectional**: Unlike regular attributes, consent changes should (and do) sync to CRM automatically if mapped. Form pre-fill needs to show current consent state.

9. **Testing needed before Henrik meeting**: Verify that pre-filled form submission on a CRM-synced profile (existing only in CRM key space) does not create duplicate profiles.

## Domain Context: Apsis One Integration Platform

**Apsis One Integrations** manages synchronization between Apsis One (a marketing platform) and external CRM systems. Current supported integrations include:

- **Efficy Enterprise 12.0** and **12.1**: Enterprise CRM systems
- **Dynamics**: Microsoft Dynamics CRM
- **E-deal**: Sales/deal management system
- **Tribe**: [Purpose unclear from this transcript]

The integration platform ensures data consistency, prevents duplicates, and protects master data from being corrupted by changes made in Apsis. Forms present a new challenge because they allow end users (not just admins) to input data that must be coordinated with CRM records.
