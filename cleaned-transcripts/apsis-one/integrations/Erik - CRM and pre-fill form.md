## Session Overview

This session brought together integration and form tool expertise to discuss the implementation of pre-filled forms with CRM synchronization. The team analyzed the existing form syncing architecture, identified critical gaps in profile resolution when sending forms to existing CRM-synced contacts, and mapped out acceptance criteria for the pre-fill feature. Key concerns emerged around preventing duplicate profiles, protecting CRM master data from unintended overwrites, and ensuring correct key space handling throughout the workflow.

---

## Current Form Syncing Architecture

### Overview of Existing Flow

[Erik Andersson]: When a form is created on a section with a CRM system that supports form syncing, the tool fires a request saying the user wants to sync the form activity to a specific CRM system. Integration registers listeners for the events available to that tool type.

For **Form Tool**, the registered events are:
- `open`
- `submitted`
- `started`
- `viewed`

For **Event Tool**, all events specified in the architecture are registered (e.g., `attended`, `cancelled`, etc.).

### Audience Subscription Worker: Event Ingestion

[Erik Andersson]: When a customer submits a form, the event comes from Audience to the **Audience Subscription Worker queue**. The worker picks up the submission and:

1. Extracts profile fields from the submission:
   - CRM ID
   - Email address
   - Phone number

2. Adds metadata required for processing:
   - Activity ID
   - Event timestamp
   - Event type
   - Profile key (generated by Audience)

> The profile key comes from Audience. For public forms with no pre-existing contact, Audience creates a new profile with an automatically assigned key.

[Lukasz Grabowski]: For public forms, the profile is created in the appropriate key space based on the data provided (email key space if email is entered, SMS key space if phone number is entered).

### Validation and Data Requirements

[Erik Andersson]: The Audience Subscription Worker validates that sufficient identifying data exists. If there is no CRM ID, the submission must have either an email address or SMS (phone number). Without at least one of these, the submission is rejected because there's no way to attach it to an existing resource:

> If there is no CRM ID, if there's no email address and no SMS, then this submission is useless. We can't do anything with it because we can't attach it to any existing resource. First name and last name alone is not enough.

### Batch Processing and Outbound Worker

[Erik Andersson]: After validation, the message is sent to Kafka. A worker then:

1. Listens to form events from the Kafka queue
2. Batches all submissions together
3. Sends the batch to the **Outbound Worker**
4. The Outbound Worker performs the actual sending to the CRM system

The Outbound Worker does not perform attribute updates on the profile in the CRM system—it only notifies the CRM that a form submission occurred.

## CRM Response Handling and Merge Logic

### Three Possible CRM Response Outcomes

[Erik Andersson]: When Integration sends a form submission to the CRM system, the CRM can respond in three ways:

**1. Empty Response (No Action)**
The CRM responds saying it accepts the event but takes no further action. Nothing additional happens on the Apsis side.

**2. Matched Record Response**
The CRM recognizes the email address or phone number as matching an existing contact in their system. The response includes:
- A `matched_record` field
- The corresponding **CRM ID** for that contact

**3. New Record Response**
The CRM doesn't recognize the contact information and creates a new contact. The response includes:
- A `new_records` field
- The newly generated **CRM ID**

### Merge Worker and Profile Consolidation

[Lukasz Grabowski]: When the CRM responds with a CRM ID (either matched or new record), the **Merge Worker** reacts to this response. The merge consolidates the form-submitted profile with the existing profile in the CRM's key space.

[Erik Andersson]: When you submit a form with an email address that matches an existing CRM contact:

1. A new profile is created in Audience with the submission event
2. The CRM system responds with the CRM ID for that matching contact
3. Integration adds the CRM ID as an attribute to the form-submitted profile
4. A merge happens between the contact created from the form and the CRM's key space

> When we install FSC Enterprise, we create an FSC key space where the CRM ID is the key. If you do it for Dynamics, you have a Dynamics key space. If you do it for E-deal, you have an E-deal key space. This is going to be very important when we come to the pre-filled forms later on.

### Why Merging Prevents Duplicates

[Erik Andersson]: The merge is critical for preventing duplicates. If the CRM sends a real-time update in the Delta Sync worker flow later, the profile will be found correctly because it's now in the CRM's custom key space. Without the merge:

> If you would have just the profile submitted from the form with the email and we had added the CRM ID, that profile would not have been found when we do the profile updates in the real time sync because we only look in our custom key space.

## Key Space Architecture and Custom Integration Key Spaces

### Bootstrap Key Spaces vs. Custom Key Spaces

[Erik Andersson]: When an integration is installed, Apsis creates a dedicated **custom key space** for that integration instance. For example:

- `FSC_Enterprise_12.1` — key space for FSC Enterprise version 12.1 installation
- `Dynamics_keyspace` — key space for Dynamics installation
- `E_deal_keyspace` — key space for E-deal installation

The CRM ID is the unique key within these custom key spaces.

[Lukasz Grabowski]: These are separate from the default bootstrap key spaces. The form data may initially be stored in email or phone key spaces, but when merged with a CRM-synced profile, the critical link is established in the integration's custom key space.

### Why Key Space Matters for Pre-filled Forms

[Erik Andersson]: This is one of the biggest pitfalls for pre-filled forms:

> When we sync data from the CRM to Apsis, the synced contact exists only in our bootstrapped key space (the custom FSC Enterprise key space, for example). It does not exist in the email key space. It does not exist in the form key space. You can only find it through our own bootstrapped key space.

This creates a critical problem when a pre-filled form is sent to a CRM-synced contact who has not previously submitted a form or been added via email separately.

## Pre-Filled Forms: Requirements and Challenges

### What Is Pre-Fill Functionality

[Lukasz Grabowski]: Pre-fill allows sending a form to a specific profile within Apsis (not a public form). When the recipient clicks the personalized form link:
- Their profile is identified in Apsis
- Form fields are automatically populated with their existing profile data
- They see a customized form with pre-filled values

The feature is currently behind a feature flag and is being rolled out to customers.

### The Profile Resolution Problem

[Erik Andersson]: The critical question: **How does the form tool find the profile to update when the form is submitted?**

When a pre-filled form is submitted, the form tool must determine which profile to update. The options are:

1. Search via the **email key space** using the email address
2. Search via the **SMS key space** using the phone number  
3. Search via the **integration's custom key space** (the CRM key space)

> I'm still a little bit unclear on how the form tool would find our integration key space from all of this. How does the form tool know which key space to search?

This is a critical gap that needs investigation.

### Scenario: CRM-Synced Contact + Prefilled Form Submission

**Scenario**: A profile was synced from the CRM to Apsis (exists only in the `FSC_Enterprise_12.1` key space). A pre-filled form is sent to this contact at their email address. They fill in the form and submit.

**Problem**: If the form tool searches using the email key space but the profile only exists in the CRM key space, it might:
- Create a new profile in the email key space with the form submission
- Leave the original CRM-synced profile untouched
- Result in two profiles for the same person (duplicate)

[Erik Andersson]: This is probably the most important use case because this is the technical part—how is our key space handled? Which key space are you merging with?

[Lukasz Grabowski]: To avoid duplicates, the result should be: one profile in Apsis. Whether searched by email or CRM ID, it should return the same profile with the same ID.

## Protecting CRM Master Data and Preventing Overwrites

### The Core Principle: CRM is Master

[Erik Andersson]: The integration architecture is built on one fundamental rule: **the CRM system is the master source of truth for synced data**. Apsis does not update CRM attributes.

> We are just letting them know: "yo, someone submitted this form." We don't update any profile. If they entered a first name or last name, Apsis is never making any actual attribute updates in the CRM system. We are not updating first names, last names, or adding email addresses. We are just letting them know that this submission happened.

### Risk: Introducing Data Discrepancies

[Erik Andersson]: If a form allows overwriting synced attributes, data discrepancies are introduced:

**Example**:
1. CRM has contact with first name = "Eric", last name = "Frederick"
2. Profile is synced to Apsis with this data
3. Contact fills out pre-filled form and changes their first name to "Henrik"
4. If Apsis accepts the override:
   - In Apsis: first name = "Henrik"
   - In CRM: first name = "Eric"
5. When the next CRM sync occurs, Apsis receives "Eric" from the CRM
6. Apsis overwrites the form-submitted "Henrik" back to "Eric"

> If you accept the overwriting of this data, now suddenly in the CRM system my name will be Eric, but in Apsis this data will be Henrik. If I send out an email to this profile, then the data displayed would be Henrik, but it should be Eric because that's what it is in the CRM system.

This creates confusion and data inconsistency.

### Solution: Check for CRM Mappings Before Allowing Updates

[Erik Andersson]: The suggested approach is to check the **Mappings Manager Service** during form submission:

1. Call the Mappings Manager Service with the account and section
2. Check if an integration is installed: `GET /mappings?account=X&section=Y&integration_id=Z`
3. Retrieve the mapping configuration which includes:
   - The Apsis field ID
   - All attributes that are mapped from the CRM

4. **Do not allow form data to overwrite attributes that are mapped from the CRM**

> If you have a field mapping on an integration, you should not be able to overwrite that data with data from the form because all of that data comes from the CRM system and if that data is to be changed, it should be changed from the CRM system instead.

### Separate Treatment: New Custom Attributes (Enrichment)

[Erik Andersson]: The rule has one important exception: **new custom attributes that are not in the CRM mapping can be added freely**.

**Example**: A form includes a new field called "Customer Satisfaction Rating" that maps to a completely new attribute in Apsis called `satisfaction_rating`. This attribute:
- Does not exist in the CRM
- Is not in any field mapping
- Can be freely updated from the form

This enriches the profile in Apsis without violating the master data principle.

> If you use a new form field called satisfaction rating which you have mapped to a completely standalone attribute inside of Apsis called satisfaction rating, then of course you can add that new data to the profile in Apsis because we will not touch it when we do the syncs because there is no field mapping.

**Critical caveat**: This enrichment data only lives in Apsis. It is never synced back to the CRM.

> The important disclaimer: this data will not exist in the CRM system. It will only exist in Apsis because we don't support the syncing of attribute changes in Apsis to the CRM.

## The CRM ID Field: An Absolute No-Go

### Why CRM ID Cannot Be Updated

[Erik Andersson]: There is one absolute prohibition: **the CRM ID field must never be allowed to be updated from a form submission**.

> If you add a field and map that to the CRM ID field inside of Apsis, and you for whatever reason would be able to actually update your CRM ID, I can tell you that we will be in deep **** because this is one of the things you can under no circumstance do if you have an integration because we will lose complete track of that profile. Then you will definitely introduce duplicates.

**Why**: The CRM ID is the unique key in the integration's custom key space. Changing it would:
- Orphan the profile from its CRM record
- Break the link between Apsis and the CRM
- Create completely new duplicates

### Implementation: Hide CRM ID from Form Editors

[Michal Rosikiewicz]: The CRM ID field should be **hidden from the form editor** when an integration is enabled on a section.

[Lukasz Grabowski]: The proposal is:
- If an integration is installed on the section → **hide the CRM ID field** from being editable in the form
- If no integration is on the section → allow the CRM ID field (for non-integrated use cases)

[Erik Andersson]: This check should be done once and the result cached across the form creation steps, rather than repeated requests.

## Consent Handling in Pre-Filled Forms

### Consent is Bidirectional

[Erik Andersson]: Unlike attribute data, **consent changes are bidirectional** and must be synced to the CRM:

> There are legal reasons as to why we need to have a bidirectional sync for consent. If an end user modifies their consent, we will send that to the CRM system if you have a mapping for it.

**Example flow**:
1. Profile in Apsis has no consent for a specific subscription
2. Pre-filled form is sent to the contact
3. Contact selects consent for that subscription and submits
4. Integration sends the consent update to the CRM system
5. CRM system receives and stores the updated consent

### Current Gap: Pre-Fill Does Not Populate Consent Checkboxes

[Lukasz Grabowski]: Currently, consent checkboxes are not being pre-filled with the profile's existing consent values. This needs to be fixed in the form tool.

> The form doesn't show the checkboxes filled. We need to fix this. If we fix it for the pre-fill, it should work out-of-the-box because we change the consent on the profile and then automatically the merge will happen.

### Integration's Role: Listening to Mapped Subscriptions Only

[Erik Andersson]: Integration only reacts to consent changes for subscriptions that exist in the **consent mapping**:

> From the integration side, we are only reacting on subscriptions that are in our consent mapping. If you have consent mapping A which is synced with the CRM, we will send those changes to the CRM. If you add it for a subscription B which does not exist in our consent mapping, we will not react on that because we don't have a listener registered for it.

## Event Logging and Audit Trail

### Current State: No Comprehensive Audit Logging

[Erik Andersson]: Integration does not currently store audit logs indicating:
- Which fields came from the CRM (source attribution)
- What changes were suggested by form submission
- What was stored locally vs. what was rejected

The absence of this logging is a gap:

> Audit logs would indicate that the service which updates the fields stores these audit logs somewhere. Today you cannot specify source when you update attributes. You can only store source when you update consent. I don't know what these audit logs would look like or where they would be stored.

This may require coordination with audit logging infrastructure.

## Form Creation Workflow: Integration Awareness

### Checking for Integration at Form Creation Time

[Erik Andersson]: When a form is created or edited, the form tool should determine whether an integration is installed on the section. This enables:

1. Hiding the CRM ID field
2. Deciding whether to show "Sync to CRM" options
3. Determining which profiles can be targeted with pre-fill
4. Applying the correct merge logic

> If you've made the request once, you will know if you should show this sync to CRM and you will know if you should hide the CRM ID. If you do the request to integration like in the last step or in the first step, I don't think that should really matter. You should do it like in the first time you need it and then preserve that data until the flow is done.

## Technical Architecture: Current vs. Required

### Current Architecture (Public Forms + CRM Sync)

```
Form Submission (Public) 
    ↓
Audience creates new profile (email/SMS key space)
    ↓
Audience Subscription Worker validates data
    ↓
Kafka queue
    ↓
Batch worker
    ↓
Outbound worker sends to CRM
    ↓
CRM responds with CRM ID (matched or new)
    ↓
Merge worker merges form profile with CRM key space
    ↓
Future CRM syncs find profile in CRM key space
```

### Required Architecture (Pre-Filled Forms + CRM Sync)

```
Pre-filled Form Link sent to CRM-synced profile
    ↓
Form tool must identify profile (CRITICAL: How? Which key space?)
    ↓
Form pre-fills with profile data
    ↓
User modifies form
    ↓
Form Submission
    ↓
Form tool must update SAME profile (not create duplicate)
    ↓
Integration must determine: is this a mapped field or custom enrichment?
    ↓
If mapped: reject or warn (CRM is master)
If custom: accept update
If consent: accept update AND sync to CRM
    ↓
Form response to CRM (if integrated)
```

## Key Takeaways

1. **CRM is Master**: All data synced from CRM should not be overwritten by form submissions. Any changes to CRM-mapped data must originate in the CRM system.

2. **Key Space Awareness is Critical**: Pre-filled forms to CRM-synced contacts must account for the custom integration key space. Profiles exist in different key spaces, and the form tool must handle merging appropriately.

3. **Duplicate Prevention Requires Careful Design**: When a pre-filled form is sent to a CRM-synced contact and they submit, the system must find and update the original CRM-synced profile, not create a new one in the email key space.

4. **Consent is Different**: Unlike attribute data, consent changes are bidirectional and should be synced to the CRM system immediately.

5. **Custom Attributes Can Be Enriched**: New attributes not present in the CRM mapping can be freely added and updated from forms without violating the master data principle.

6. **CRM ID is Sacred**: The CRM ID field must be strictly protected from form editing. If overwritten, the link between Apsis and CRM is broken, guaranteeing duplicates.

7. **Attribute Push to CRM is Out of Scope**: The current architecture doesn't support pushing enriched attributes back to the CRM. This would require new feature development on both Integration and CRM sides.

8. **Form Tool Must Be Integration-Aware**: The form tool needs to understand when an integration is installed and apply appropriate logic for key space resolution, field mapping checks, and merge decisions.
